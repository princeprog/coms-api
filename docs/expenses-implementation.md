Approved 2026-10-25. Replace the Costs & profit sidebar entry with Expenses, retain /costs and secondary Product & stock costs link. Operating expenses count immediately. ## Shared API contract

All routes authenticated and gateway/access guarded. Monetary values decimal strings. Dates YYYY-MM-DD in Asia/Manila; instants ISO. Sources OPERATING, SUPPLIER_DELIVERY, DIRECT_PURCHASE. Status RECORDED or VOIDED. Payment CASH, BANK_TRANSFER, EWALLET, CARD, OTHER. Cash source REGISTER or OTHER only for CASH; null otherwise. Location: scope COMMISSARY with branch_id null, or BRANCH with branch_id UUID.

- GET /expenses: query from,to (default Manila current month), scope (optional), branch_id (optional), category_id (UUID or STOCK_PURCHASES), source (optional), status (RECORDED default, VOIDED, all), search, sort (newest default, oldest, amount_highest, amount_lowest), page, page_size (10/30/50). Response {items,total,page,page_size,summary:{recorded_spending,operating_expenses,stock_purchases},by_location:[{id,name,amount}],by_category:[{id,name,amount}]}. Aggregates always exclude VOIDED entries even when inspecting history; same remaining filters and same DB snapshot. Use no floats. Each item: {id,source,expense_date,scope,branch_id,location_name,category_id,category_name,description,amount,payment_method,cash_source,cash_movement_id,payee,reference,notes,status,revision,created_by_user_id,created_by_name,created_at,updated_at}. Imported purchase optional fields null, revision 1, status RECORDED, category_id STOCK_PURCHASES, location Commissary. id is UUID and source+id is client row key.
- GET /expenses/records/:source/:id: {record: item,history:[{id,action,reason,actor_name,created_at,before,after}]}. Imported purchases history [] and optional source_href string if source read permission; otherwise null. Operating detail shows own audited history without audit.read.
- POST /expenses: {expense_date,scope,branch_id,category_id,description,amount,payment_method,cash_source,cash_movement_id,payee,reference,notes}; Idempotency-Key required. Returns operating detail shape. Required description; optional payee/reference/notes nullable. Dates not future; amount >0, max 999999999.99, two decimals. Text limits description/payee 160, reference100, notes1000, correction reason500.
- PATCH /expenses/:id: full create fields + revision + reason; Idempotency-Key required. Returns detail. Requires old/new location access. Linked record's scope/branch/amount/cash source/payment/cash movement immutable; void/recreate to correct those. For unlinked edits, new register link may be selected subject to validation. Keep inactive category/location only if unchanged for history corrections; new/changed location/category must be active.
- POST /expenses/:id/void: {revision,reason}; Idempotency-Key required, returns detail. No edits/restoration of voided expense. Matching retries return existing result; conflicting retry payloads 409.
- GET /expenses/cash-outs: branch_id required, search?, page,page_size. Response {items:[{id,shift_id,shift_number,business_date,amount,reason,actor_name,created_at}],total,page,page_size}. Only OUT movements not linked to RECORDED expenses; shifts.read and (shift owner or shifts.review) required, and expense location access. Open or closed historical shifts allowed. No expected cash exposure.
- GET /expenses/locations: {items:[{scope,branch_id,name,is_active}]}; only permitted commissary/branches, include inactive for historical filters, frontend exclude inactive for new form choices.
- GET /expenses/categories: {items:[{id,name,is_active,created_at,updated_at}]}; expenses.read. Returns all categories incl inactive (historical/form-selected values); excludes virtual STOCK_PURCHASES. POST same route {name}; PATCH /expenses/categories/:id {name?,is_active?}; category_manage required, no delete. Returns category. Reserved Stock purchases forbidden, unique case-insensitive trimmed names.
- GET /expenses/export: same filters, existing audited CSV export with 50,000-row cap, no page/pagination restriction on total. include source/location/category/payment/status fields. No mutation of receipts or cash.

Permissions: expenses.read, expenses.global_read (all branches only), expenses.commissary_read, expenses.create, expenses.update, expenses.void, expenses.categories_manage. All read routes require read. Global/commissary permissions widen location scope only, never imply mutation grants. SuperAdmin bypass. Predefined BRANCH_MANAGER: read/create/update/void. COMMISSARY_MANAGER: read/commissary_read/create/update/void. Custom roles/cashiers unchanged. Commissary read authorizes purchase-value summary/detail through Expenses; source links require supplier_receipts.read. Categories default admin-only. Branch access includes inactive historical branches using assigned IDs; writes enforce active.

## Database owned by parent implementation

public.expenses: id UUID default; expense_date date; inventory_scope varchar COMMISSARY|BRANCH; branch_id nullable FK; category_id FK; description varchar160; amount numeric(11,2); payment_method varchar; cash_source nullable varchar; cash_movement_id nullable FK register_shift_cash_movements; payee varchar160 nullable; reference varchar100 nullable; notes varchar1000 nullable; status varchar RECORDED default; revision integer1; created_by_user_id/updated_by_user_id FK coms_auth.users; created_at/updated_at timestamptz defaultnow. CHECK scope/branch, valid payments/cashlinks, >0 amount. Partial unique cash_movement_id where status=RECORDED. No hard-delete API.

Append-only DB trigger. API additionally calls recordAudit for expense/category mutation with actor/branch and meaningful labels.

## History and release safeguards

Detail reads authorize every event's before and after location, independently of the expense's current location. Events involving an inaccessible location are omitted completely, including their reason. This prevents transferring an expense from revealing earlier location-private notes or amounts. Authorized administrators retain complete history.

Release the additive migration and API before the frontend. Confirm the production target, verify a restorable backup and migration status before applying; production migration/deployment is not performed by this implementation. Existing receipts are projected dynamically, so no expense import or purchase backfill is needed. Do not roll back the schema after operational expense history, edited categories or custom grants exist. Reverting the frontend navigation alone retains the ledger safely.

The API never changes inventory movements, register cash movements, shift reconciliation, daily reports or profit calculations when an expense is recorded, corrected or voided. Voiding releases its cash-out classification for a replacement expense; it does not refund money. No hard-delete or restore endpoint exists.
